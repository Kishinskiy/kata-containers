# Обзор

**[Kata Container](https://github.com/kata-containers)** использует виртуальную машину (VM) для повышения безопасности и изоляции рабочих нагрузок контейнеров. В результате система имеет ряд отличий и ограничений по сравнению со стандартной средой выполнения **[Docker*](https://www.docker.com/)** **[`runc`](https://github.com/opencontainers/runc)**.

Некоторые из этих ограничений имеют потенциальные решения, в то время как другие существуют из-за фундаментальных архитектурных различий, как правило, связанных с использованием виртуальных машин.

**[Среда выполнения Kata Container](../src/runtime)** запускает каждый контейнер в своей собственной аппаратно-изолированной виртуальной машине, и каждая VM имеет свое собственное ядро. Из-за этой более высокой степени изоляции определенные возможности контейнеров не могут быть поддержаны или неявно включены через виртуальную машину.

# Определение ограничения

**[Спецификация времени выполнения](https://github.com/opencontainers/runtime-spec)** ("OCI spec") от **[Инициативы по открытым контейнерам (Open Container Initiative)](https://www.opencontainers.org/)** определяет минимальные спецификации, которые должна поддерживать среда выполнения для взаимодействия с менеджерами контейнеров, такими как Docker. Если среда выполнения не поддерживает какой-либо аспект спецификации OCI, по определению это является ограничением.

Однако эталонная реализация среды выполнения OCI (`runc`) не идеально соответствует самой спецификации OCI.

Кроме того, поскольку средой выполнения OCI по умолчанию, используемой Docker, является `runc`, Docker ожидает, что среды выполнения будут вести себя так же, как `runc`. Это implies, что возникает другая форма ограничения, если поведение реализации среды выполнения не совпадает с поведением `runc`. Наличие двух стандартов усложняет задачу поддержки среды Docker, поскольку среда выполнения должна поддерживать официальную спецификацию OCI и нестандартные расширения, предоставляемые `runc`.

# Вопросы в ожидании решения

В этом разделе перечислены элементы, которые, возможно, удастся исправить.

## Команды CLI OCI

### Поддержка Docker и Podman
В настоящее время Kata Containers не поддерживает Podman.

См. issue https://github.com/kata-containers/kata-containers/issues/722 для получения дополнительной информации.

Docker поддерживает Kata Containers, начиная с версии 22.06:

```bash
$ sudo docker run --runtime io.containerd.kata.v2
```

Kata Containers отлично работает с containerd, мы рекомендуем использовать инструмент командной строки в стиле Docker от containerd **[`nerdctl`](https://github.com/containerd/nerdctl)**.

## Команды среды выполнения

### checkpoint и restore

Среда выполнения не предоставляет команды `checkpoint` и `restore`. Ведутся обсуждения об использовании сохранения и восстановления состояния виртуальной машины для предоставления функциональности, подобной **[`criu`](https://github.com/checkpoint-restore/criu)**, что может стать решением.

Обратите внимание, что стандарт OCI не определяет команды `checkpoint` и `restore`.

См. issue https://github.com/kata-containers/runtime/issues/184 для получения дополнительной информации.

### Команда events

Среда выполнения не полностью реализует команду `events`. Уведомления `OOM` и статистика `Intel RDT` не полностью поддерживаются.

Обратите внимание, что стандарт OCI не определяет команду `events`.

См. issue https://github.com/kata-containers/runtime/issues/308 и https://github.com/kata-containers/runtime/issues/309 для получения дополнительной информации.

### Команда update

В настоящее время не поддерживается только вес блочного I/O.
Все остальные конфигурации поддерживаются и работают правильно.

## Сетевое взаимодействие

### Сеть хоста (Host network)

Сеть хоста (`nerdctl/docker run --net=host` или **[Kubernetes `HostNetwork`](https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/pod-v1/#hosts-namespaces)**) не поддерживается. Невозможно получить прямой доступ к сетевой конфигурации хоста изнутри виртуальной машины.

Опция `--net=host` по-прежнему может использоваться с контейнерами `runc` и смешиваться с запущенными Kata Containers, что позволяет использовать `--net=host` при необходимости.

Следует отметить, что в настоящее время передача опции `--net=host` в Kata Container может привести к тому, что сетевая настройка Kata Container изменит, перенастроит и, следовательно, возможно, нарушит сетевую настройку хоста. Не используйте `--net=host` с Kata Containers.

### Поддержка присоединения к существующей сети VM

Docker поддерживает возможность присоединения контейнеров к пространству имен другого контейнера с помощью синтаксиса `docker run --net=containers`. Это позволяет нескольким контейнерам совместно использовать общее сетевое пространство имен и сетевые интерфейсы, размещенные в этом сетевом пространстве имен. Kata Containers не поддерживает совместное использование сетевого пространства имен. Если Kata Container настроен на совместное использование сетевого пространства имен контейнера `runc`, среда выполнения фактически захватывает все сетевые интерфейсы, назначенные пространству имен, и привязывает их к виртуальной машине. Следовательно, контейнер `runc` теряет сетевое соединение.

### docker run --link

Среда выполнения не поддерживает команду `docker run --link`. Эта команда теперь устарела в docker, и мы не намерены добавлять ее поддержку. Эквивалентная функциональность может быть достигнута с помощью более новых сетевых команд docker.

См. дополнительную документацию на **[docs.docker.com](https://docs.docker.com/network/links/)**.

# Архитектурные ограничения

В этом разделе перечислены элементы, которые, возможно, не будут исправлены из-за фундаментальных архитектурных различий между "мягкими контейнерами" (т.е. традиционными контейнерами Linux*) и контейнерами на основе виртуальных машин.

## Ограничения хранилища

### Kubernetes `volumeMounts.subPaths`

Kubernetes `volumeMount.subPath` в настоящее время не поддерживается Kata Containers.

См. **[это issue](https://github.com/kata-containers/runtime/issues/2812)** для более подробной информации.
**[Другое issue](https://github.com/kata-containers/kata-containers/issues/1728)** посвящено случаю `emptyDir`.

### Тома Kubernetes [hostPath][k8s-hostpath]

В Kata тома Kubernetes hostPath могут монтировать каталоги и обычные файлы хоста в гостевую виртуальную машину через общий доступ к файловой системе, если это включено через флаг конфигурации `shared_fs` **[configuration][runtime-config]**.

По умолчанию:

*   Среда без TEE (Trusted Execution Environment): Для монтирования файлов хоста используется общий доступ к файловой системе.
*   Среда TEE: Общий доступ к файловой системе отключен. Вместо этого файлы хоста копируются в гостевую виртуальную машину при запуске контейнера, и изменения файлов *не* синхронизируются между хостом и гостем.

В некоторых случаях поведение томов hostPath в Kata дополнительно отличается по сравнению с контейнерами `runc`:

**Монтирование блочных устройств хоста**: Когда том hostPath имеет тип **[`BlockDevice`][k8s-blockdevice]**, Kata подключает (hotplugs) блочное устройство хоста к гостю и предоставляет его напрямую контейнеру.

**Монтирование устройств гостя**: Когда исходный путь тома hostPath находится внутри `/dev` (или сам `/dev`), и путь соответствует не обычному файлу (т.е. устройству, каталогу или любому другому специальному файлу) или недоступен для shim Kata, агент Kata выполняет bind mount исходного пути напрямую из *гостевой* файловой системы в контейнер.

[runtime-config]: /src/runtime/README.md#configuration
[k8s-hostpath]: https://kubernetes.io/docs/concepts/storage/volumes/#hostpath
[k8s-blockdevice]: https://kubernetes.io/docs/concepts/storage/volumes/#hostpath-volume-types

### Монтирование `procfs` и `sysfs`

По соображениям безопасности следующие операции монтирования запрещены:

| Тип               | Источник   | Назначение                       | Обоснование     |
|-------------------|-----------|----------------------------------|-----------------|
| `bind`            | `!= proc` | `/proc`                          | CVE-2019-16884  |
| `bind`            | `*`       | `/proc/*` (см. исключения ниже)  | CVE-2019-16884  |
| `proc \|\| sysfs` | `*`       | не каталог (например, symlink)   | CVE-2019-19921  |

Для bind mounts под /proc разрешены следующие назначения:

*   `/proc/cpuinfo`
*   `/proc/diskstats`
*   `/proc/meminfo`
*   `/proc/stat`
*   `/proc/swaps`
*   `/proc/uptime`
*   `/proc/loadavg`
*   `/proc/net/dev`

## Привилегированные контейнеры (Privileged containers)

Поддержка привилегированного режима в Kata fundamentally отличается от контейнеров `runc`. Контейнер запускается с повышенными capabilities внутри гостевой ОС. Это также верно при использовании `securityContext privileged=true` в Kubernetes.

Важно отметить, что поведение по умолчанию, заключающееся в передаче устройств хоста привилегированному контейнеру, не поддерживается в Kata Containers, и его необходимо отключить, см. **[Привилегированные Kata Containers](how-to/privileged.md)**.

## Гостевые образы контейнеров (Guest pulled container images)

При использовании таких функций, как **nydus guest-pull**, явно задавайте идентификаторы пользователей/групп (user/group IDs) в спецификации pod.
Если значения ID опущены:

*   Ваша рабочая нагрузка может быть выполнена с непредвиденными значениями ID пользователя/группы, потому что слои образов могут быть недоступны для containerd, поэтому конфигурация образа (включая пользователя/группу) не применяется.
*   Если используется policy или genpolicy, сгенерированная политика может обнаружить эти непредвиденные значения и отвергнуть создание контейнеров рабочей нагрузки.

Явно задавайте `securityContext`. Используйте **pod-level** `spec.securityContext` (для Pod) или `spec.template.spec.securityContext` (для контроллеров, таких как Deployments) и/или **container-level** `spec.containers[].securityContext`. Включите как минимум:
*   `runAsUser` — основной ID пользователя
*   `runAsGroup` — основной ID группы
*   `fsGroup` — право собственности на группу томов (часто отражается как дополнительная группа)
*   `supplementalGroups` — список дополнительных ID групп (если необходимо)

Пример:

```yaml
# Явное указание пользователя/группы/дополнительных групп для поддержки nydus guest-pull
securityContext:
  runAsUser: 0
  runAsGroup: 0
  fsGroup: 0
  supplementalGroups: [1, 2, 3, 4, 6, 10, 11, 20, 26, 27]
```

# Приложения

## Задача ограничений (The constraints challenge)

Применение ограничений ресурсов, таких как cgroup, CPU, память и хранилище, к рабочей нагрузке не всегда straightforward в системе на основе виртуальных машин. Kata Container работает в изолированной среде внутри виртуальной машины. Это в сочетании с архитектурой Kata Containers открывает гораздо больше возможностей, чем доступно традиционным контейнерам Linux, из-за различных уровней и контекстов.

В некоторых случаях может потребоваться применить ограничения на нескольких уровнях. В других случаях аппаратно-изолированная виртуальная машина предоставляет функциональность, эквивалентную запрошенному ограничению.

Следующие примеры outline некоторые из различных областей, где можно применять ограничения:

*   Внутри виртуальной машины
    Ограничьте гостевое ядро. Этого можно достичь, передав определенные values через командную строку ядра, используемую для загрузки гостевого ядра. Alternatively, значения sysctl могут быть applied при ранней загрузке.

*   Внутри контейнера
    Ограничьте контейнер, созданный внутри виртуальной машины.

*   Вне виртуальной машины:
    *   Ограничьте процесс гипервизора, применив ограничения на уровне хоста.
    *   Ограничьте все процессы, работающие внутри гипервизора.
        Этого можно достичь, указав определенные опции конфигурации гипервизора.

Обратите внимание, что в некоторых обстоятельствах может потребоваться применить определенные ограничения к более чем одной из предыдущих областей для достижения желаемого уровня изоляции и контроля ресурсов.
